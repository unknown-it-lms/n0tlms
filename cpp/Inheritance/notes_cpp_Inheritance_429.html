Inheritance
  • Many times we need to create a more specialized form of an entity we already have in our system. For example, we already have an entity Person, modeled using class Person in our system.
  • This entity Person can be re-used for creating specialized types of persons like Employee. Note this is possible because every Employee is always a person first. It has all state and behavior of a person, to which, some more state and behavior is added to make it a more special type of person called as Employee.
  • Same is true for a Player also. The entity Person can be re-used for creating specialized types of persons like Player. Note this is possible because every Player is always a person first. It has all state and behavior of a person, to which, some more state and behavior is added to make it a more special type of person called as Player.
  • Inheritance makes such reuse possible in object oriented programming.
Concepts and terminologies
1Inheritance is re-using existing entity (class) to create more specific forms of similar type.
2The class which is re-used is called base class (or Super class in other languages like Java) and the new class created from it is called derived class (or sub class in other languages like Java).

​​​​​​​Refer the inheritance diagram given below:
Here, Person is base class (super class) and Employee is derived class (Sub class). Programmer is base class (super class) and DotNetProgrammer is derived class (Sub class).   
3We can further derive more specific classes from the derived classes. This way we create an hierarchy of classes which is called as inheritance hierarchy.
4Inheritance creates IS-A type of relationship between the two classes. This is because every derived type IS always of the base type. For example, every Player IS-A person and every Employee IS-A person.
5Classes at the top represent general entities and those at bottom represent more specific entities. For Example: Person is a general entity but Employee is more specific than Person. Manager is more specific entity than Employee and so on.
6​
7As we move down the hierarchy, we are moving from generalization to specialization.
8The derived class inherits entire state and entire behavior of the base class. It can only add more state and more behavior. Hence, everything we expect from base class can always be expected from the derived class.
9The IS-A relationship is applicable at single level as well as at multiple levels of inheritance. For example, every Employee IS-A Person, every Manager IS-A Employee. Hence, every Manager IS-A Person also. Similarly, we can say that every ProjectManager is Employee, every SalesManager is a Person, every DotNetProgrammer IS-A Person, every Programmer is Employee and so on... 
10As the derived class ALWAYS support entire state and behavior of base class, we can always provide an object of derived class where ever object of base class is needed. For example, If Person is needed for a task, it can be assigned to an Employee. If Programmer is needed for a task, we can provide JavaProgrammer. If Manager is needed for a task, we can always provide ProjectManager. This is called as Principle of Substitution, which say that "We can substitute objects of base class with any object of derived class in a software system".
11The IS-A relationship is unidirectional. Every SalesManager IS-A manager BUT every Manager may not be a SalesManager. Every Programmer IS-A Employee BUT every Employee may not be a Programmer. Hence, the arrow should point from sub class to super class.

Order of execution of constructor and destructor
  • Where we create object of a derived class, constructors are executed in the order of base to derived.
  • When the object of derived class gets destroyed, destructors are called in the order of derived to base.

This can be understood from the following example.

In this case, the data  members of class Person get inherited in class Programmer from class Player as well as class Employee. This creates lot of issues in accessing these data members as there are more than one copies of the data. This problem is called as Diamond-ring problem in C++.

Protected
We have already seen access specifiers like private and public. Inheritance adds a new access specifier called 'protected'. Any class member declared with protected access specifier can be accessed in any class derived from it directly or indirectly.  

Lets see its implementation as follows:

Declaration of Person and EmployeeEmployee.cpp

class Person
{   
    char Name[30]; // private, by default
protected:
    int d,m,y;
public:
    Person();
    Person(char*,int,int,int);
    void Display();
};

class Employee :: public Person {
    int empId;
    float basicSal;
public:   
     void Display();
};		void Employee::Display()
{
    cout<< Name; /* Error: Name is declared as private in base class. So it CAN NOT be accessed in the derived class Employee*/

    cout <<d<<m<<y; /*OK. d, m and y is declared as protected in base class Person. Hence it can be accessed in any class derived from Person*/

    cout<<empId<<basicSal; /* OK. Private  data of class Employee can be accessed in member function of same class.*/
}


Protected data can be access at level in the hierarchy, as shown below:

class A {
    protected:
    int a1;
};
class B :: public A {
    public:
    void functionB() {
        this->a1=10; // OK
    }
};
class C :: public B {
    public:
    void functionC() {
        a1=20; // OK
    }
};
class D :: public C {
    public:
    void functionD() {
        this->a1=30; // OK
    }
};		Note here that:
  • The protected data of class A is directly accesible in class B as well as class C and class D. This proves that, protected members can be access directly in any class derived directly or indirectly (in multiple levels of inheritance)
  • Also note that in some cases, we have accessed a1 using this pointer and in other cases without this pointer. Both are accepted in this case, because there is not other local variable or data member, with same name in the derived classes.

Review of all access specifiers in C++:
C++ has three access specifiers:
  1. private: Can be accessed only within the class in which it is declared
  2. protected: Can be accessed from any class derived from it directly or indirectly.
  3. public: Can be access from anywhere, irrespective of class hierarchy.
 

Diamond ring problem
Consider the hybrid inheritance we have discussed earlier. ​​​​​
​class Person 
{
    protected: 
        char Name[30];
};
class Player :: public Person {
    // data member Name inherited from base class Person
};
class Employee :: public Person {
    // data member Name inherited from base class Person
};
class Programmer :: public Player, public Employee {

    /* data member Name inherited from base class Player as well as base class Employee */
    public:
        void Display()
        {    
            cout<<Name; /* Error: We have two copies of Name in this class. So compiler can not decide which copy to access here. So it gives error. 
This problem is called as Diamond-ring problem in C++. */
        }
};
Temporary solution:We can explicitly specify which copy to access. For example, cout<<Player::Name will access the Name varible inherited via base class Player. Simillarly, Employee::Name will access the Name varible inherited via base class Employee.
Though, this approach removes the error during compilation, it is not a complete solution, because it doesn't prevent two copies of Name in the class Programmer. 
A better solution to Diamond-ring problem is given by Virtual inheritance mentioned below.
Virtual inheritance
Virtual inheritance solves the Diamond-ring problem by allowing only one copy of data member inherited through two base classes. This can be done as shown below:
​
Note that: the virtual keyword is used for deriving class Player and class Employee from class Person.		class Person 
{
    protected: 
        char Name[30];
};
class Player :: virtual public Person {
    // data member Name inherited from base class Person
};
class Employee :: virtual public Person {
    // data member Name inherited from base class Person
};
class Programmer :: public Player, public Employee {

    /* data member Name inherited from base class Player only. This prevents multiple copies of that data*/
    public:
        void Display()
        {    
            cout<<Name; /*Ok. There is only one copy of Name now */
        }
};
